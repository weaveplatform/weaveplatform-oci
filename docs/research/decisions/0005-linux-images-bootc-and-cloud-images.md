# 0005: Linux images: bootc source of truth, cloud images fallback

Status: Proposed

## Context

Linux is the one guest with no weave artifact today. guestweave-cli-macos creates an
empty EFI VM and expects the user to mount an installer ISO or pull a third-party
image. guestweave-cli-windows builds a native kernel and debootstrap rootfs in WSL,
or installs from a distribution ISO with a kickstart or autoinstall side volume.
hostweave's QEMU runtime reads a local qcow2 named in an environment variable and the
scheduler can never place a resolved VM image on it. The agent-modules handoff records
a decision that "the image is the unit of trust" and that the Linux agent is a signed
`.deb` installed by cloud-init, but no image with the agent baked in has been built.
Linux is also the only guest OS the organisation may publish publicly, which makes it
the right first end-to-end exercise of the whole pipeline.

## Decision

**Source of truth.** Where a distribution offers a bootc base (Fedora, CentOS Stream,
and derivatives), the Linux image is defined as a bootc container image: a
`Containerfile` that starts `FROM quay.io/fedora/fedora-bootc:<ver>`, installs the
weave agent packages from the signed apt or dnf repository, strips SSH host keys and
machine identity, and carries `LABEL containers.bootc=1`. The container image is built
and pushed first; the VM disk is derived from it with `bootc-image-builder`
(`image-builder`) using `--type raw`. Day-two updates inside a running guest may use
`bootc upgrade` from the same registry reference; the published disk is bootstrap
media, not the only path to the latest content.

**Fallback.** Where no bootc base exists or is wanted (Ubuntu, Debian), the image starts
from the distribution's cloud image, verified against the distribution's signed
checksum file, converted to raw with `qemu-img convert -O raw`, booted once under
QEMU with a NoCloud seed that installs the agent and performs the same stripping, then
shut down and packed.

**Artifact.** Both paths produce the same `weave-guest-v1` artifact
([0001](0001-vm-artifact-contract.md)): raw disk chunks, `firmware.type: uefi`, no
state blob carried (the UEFI variable store is regenerated by every consumer), one
index child per architecture built (`linux/amd64`, `linux/arm64`), and
`com.deploymenttheory.weave.guest.guest.distro` plus `guest.osVersion` annotations because
`platform.os.version` is omitted for linux. The config records the upstream media
(`build.sourceMedia[]` with `kind: bootc` or `kind: cloud-image`, URI and digest).

**Consumers.** hostweave's QEMU runtime pulls through the shared cache, keeps the raw
base, and creates a qcow2 overlay per attempt with `qemu-img create -f qcow2 -b <base>
-F raw`. guestweave-cli-macos boots the raw disk under Virtualization.framework with a
fresh `machineidentifier.bin`. guestweave-cli-windows converts raw to VHD or VHDX for
HCS, or keeps its native kernel-and-rootfs path for non-image Linux guests. The
cloud-init NoCloud seed stays the per-instance provisioning mechanism on every
hypervisor; the image never carries an instance identity.

**Publication.** Linux repositories under `ghcr.io/deploymenttheory/weave-images/` may
be public. Modified Ubuntu images are named without the Ubuntu trademark in a way that
complies with Canonical's policy; Fedora-derived images are labelled as a remix where
the Fedora trademark guidelines require it; RHEL content is never published.

## Rationale

A bootc image is already an OCI image with content-addressed layers, so the OS
definition, the build inputs and the provenance all live in the same registry and
the same trust chain as the derived disk. Deriving the disk with the distribution's
own tooling avoids writing an installer. The cloud-image fallback exists because the
largest fleets of developer and CI guests run Ubuntu, which has no bootc base. Raw as
the only disk encoding keeps Linux inside the single contract; every hypervisor in the
fleet consumes raw directly or through a cheap local conversion.

Alternatives considered:

- **KubeVirt containerDisk.** A qcow2 inside a tar layer, consumable by KubeVirt, CDI,
  crun-vm and Kubernetes image volumes. Rejected for publication because it is a second
  format, single-layer, gzip-only and capped at 10 GB on GHCR; Kubernetes is not a weave
  consumer. It remains the obvious export format if that changes.
- **Packer QEMU builds from ISO with kickstart or autoinstall.** Reproducible but slow
  and distribution-specific; the Windows CLI already does this for local use. Kept as a
  local from-source mode, not as the publication path.
- **mkosi or diskimage-builder.** Capable, but they define the OS outside the registry.
  Rejected in favour of bootc where available.
- **qcow2 as the artifact encoding.** Smaller when sparse, but it is QEMU's format,
  Virtualization.framework does not boot it, and chunk offsets would no longer be guest
  LBAs. Rejected; sparse handling is done by zero-chunk elision instead.

## Constraints

- `bootc-image-builder` runs as a privileged container on a Linux host; in GitHub
  Actions that is a hosted `ubuntu-*` runner with KVM, inside roughly 14 GB of disk.
- arm64 derivation on hosted runners is slow or requires an arm64 runner; the matrix
  may need self-hosted capacity.
- Debian publishes only `SHA512SUMS` without a detached signature for its cloud images;
  Ubuntu, Fedora, AlmaLinux and Rocky publish signed checksum files. The pipeline records
  which verification was possible.
- bootc explicitly does not package disk images as OCI artifacts; the weave contract
  does that, and nothing in bootc depends on it.
- The signed `.deb` repository and the dnf equivalent are owned by
  `weaveplatform-agent`; this record assumes they exist for every published
  distribution.

## Verification

- `build-linux.yml` produces an artifact from `fedora-bootc` and from the Ubuntu
  cloud image, both passing the conformance suite.
- A boot test on a hosted `ubuntu-*` runner: pull the artifact with `weaveoci pull`,
  create the overlay, boot under QEMU with a NoCloud seed, and confirm the agent
  service starts and the hypervisor channel authenticates (the gate the Linux
  bring-up handoff defines).
- hostweave `agent/runtime/qemu` tests: pull from an in-process registry, overlay
  created with `-F raw`, seed attached, `HOSTWEAVE_QEMU_IMAGES` no longer read.
- Checksum verification test per distribution against recorded fixtures.
- Existing evidence: `deploymenttheory/weaveplatform-agent-modules@main handoff/linux-bring-up.md`
  (agent installed via NoCloud seed, channel authenticated against a real Debian guest).
