# 0012: Container images published by weaveplatform-oci

Status: Proposed

## Context

The private and hybrid profiles ([0011](0011-deployment-profiles-and-reference-registry.md))
need two things:

- a registry that runs as a container with weave's settings applied; and
- a publisher that runs in any CI system, not just GitHub Actions.

The project owner chose to have weaveplatform-oci publish its own container images to
GHCR rather than ship only a Compose file that points at upstream zot.

The upstream zot image has the following properties:

- It is built with stacker on `gcr.io/distroless/base-nossl-debian13`.
- It has an architecture-specific binary path.
- It runs as root.
- It has no shell or HTTP client.
- It carries no cosign signatures.

The `weaveoci` CLI is CGO-free Go.

## Decision

**`ghcr.io/weaveplatform/weaveoci`.**

- Built with ko v0.19.1 from `./cmd/weaveoci`.
- Base `gcr.io/distroless/static-debian13:nonroot`, named by tag in `.ko.yaml`. ko
  resolves the tag at build time and records the base digest in the image's
  `org.opencontainers.image.base.digest` annotation, so each release starts from the
  current distroless.
- Platforms linux/amd64 and linux/arm64.
- The same release also publishes `weaveoci` binaries for darwin/arm64, darwin/amd64,
  windows/amd64, windows/arm64, linux/amd64 and linux/arm64 as release archives with
  SHA-256 sums.
- The image's entrypoint is `weaveoci`. A private-profile pipeline in any CI system can
  run `docker run ghcr.io/weaveplatform/weaveoci publish …`.

**`ghcr.io/weaveplatform/weave-zot`.**

- Built with `docker/build-push-action` v7.4.0 from `deploy/zot/Dockerfile`.
- The Dockerfile starts `FROM ghcr.io/project-zot/zot:v2.1.21@sha256:<index digest>`,
  pinned by digest.
- It copies in the two configuration roles to `/etc/zot/roles/private.json` and
  `/etc/zot/roles/mirror.json`. The private role is also the default
  `/etc/zot/config.json`.
- It also copies in a static `weaveoci` binary used only for
  `HEALTHCHECK CMD ["/usr/local/bin/weaveoci","healthcheck","--url","http://127.0.0.1:5000/readyz"]`.
- Platforms linux/amd64 and linux/arm64. The build only copies files, so no emulation
  is needed.
- The image keeps the upstream root user in v1. Running as non-root is a documented
  hardening option with a writable volume.

**Reference Compose deployment.**

- `deploy/zot/compose.yaml` runs `weave-zot` with a named volume at
  `/var/lib/registry`.
- It mounts an htpasswd file and TLS material.
- A `profile` switches between the store and mirror roles.
- It contains no secrets. Its README gives the setup commands: create users, upload the
  cosign public key to `/v2/_zot/ext/cosign`, and validate the config with `zot verify`.

**Release and supply chain.**

- Both images are released by `.github/workflows/release-images.yml` when
  release-please tags `vX.Y.Z`.
- Tags are `X.Y.Z`, `X.Y` and `latest`.
- Both are signed keyless with cosign v3.1.3 in Actions, using the GitHub OIDC
  identity.
- Both carry an SPDX SBOM, generated by syft (`anchore/sbom-action`) from the pushed
  image and attached as a cosign attestation (`cosign attest --type spdxjson`).
- GitHub build provenance (`actions/attest` v4.2.2, `push-to-registry: true`) is added
  when the repository is public. For a private repository it needs GitHub Enterprise
  Cloud, and the organisation is on the Team plan (Q13).
- The same workflow uploads the `weaveoci` release archives and `SHA256SUMS` to the
  GitHub release that release-please created.
- Both packages are public. They contain no OS images, so the licensing constraints do
  not apply.

**Upstream bumps.** Dependabot (or Renovate) proposes new upstream zot digests and Go
module versions. A bump merges only when the acceptance suite passes against the new
image ([0013](0013-quality-gates.md)).

## Rationale

Baking the configuration into a published image makes the settings that matter for
multi-GiB artifacts the default:

- timeouts disabled;
- `gcDelay` above the longest push;
- CVE download off;
- authentication on;
- immutability through access control.

An operator does not have to rediscover them.

Copying a static `weaveoci` into the image gives the distroless container a healthcheck
without adding a shell.

ko builds the CLI image reproducibly from Go with no Dockerfile, and produces an SBOM by
default.

A plain Dockerfile is the simplest correct way to extend an upstream image that ko
cannot build.

Keyless signing and attestation in Actions give anyone a public way to check the images
with `cosign verify` or `gh attestation verify`.

Alternatives considered:

- **GoReleaser `dockers_v2` or `kos`.** Capable, but it is a second build orchestrator
  next to release-please. Its `kos` defaults to linux/amd64 only. Rejected for v1; it can
  replace ko later if GoReleaser takes over binary releases.
- **Publish only a Compose file that uses upstream zot.** Rejected by the project owner.
  It leaves every operator to apply the large-artifact settings by hand.
- **Docker Hub.** Pull rate limits and a separate account. GHCR keeps images next to
  the code. Rejected.
- **Build zot from source.** Rejected: it duplicates upstream's stacker build and its
  extension set.

## Constraints

- Upstream zot images carry no signatures, so the base is trusted by digest pin only.
- The weave-zot image inherits root execution and the architecture-specific binary path
  from upstream.
- freebsd platforms exist upstream but are not published by weave.
- An image built for a version tag and then re-tagged is the same digest. Tags other
  than `X.Y.Z` move.

## Verification

- `release-images.yml` builds both images on every pull request without pushing, and
  brings up the reference Compose deployment: the container must report healthy,
  anonymous requests must get 401 and the publisher 200.
- The acceptance suite runs against the freshly built `weave-zot` image, including
  `phase2b_weave_zot.feature`: authentication, publisher-create and admin-update tag
  rules, and an on-demand mirror that preserves index digests and signature referrers.
- After push, the workflow runs these by digest and fails the release on error:
  - `cosign verify --certificate-identity-regexp '^https://github\.com/weaveplatform/weaveplatform-oci/\.github/workflows/release-images\.yml@refs/tags/v' --certificate-oidc-issuer https://token.actions.githubusercontent.com <image>@<digest>`
  - `cosign verify-attestation --type spdxjson` with the same identity
  - `gh attestation verify oci://<image>@<digest> -R weaveplatform/weaveplatform-oci`,
    when the repository is public
  - `zot verify` for both roles, run inside the published `weave-zot`
- A container test starts `weave-zot` and checks that the healthcheck reports healthy.
- `zot verify` passes for both config roles.
